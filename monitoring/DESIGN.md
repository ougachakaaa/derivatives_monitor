# Monitoring 设计取舍

本文件只解释 Monitoring 内部为何这样组织。Market Facts、可重建派生值与应用事实的跨模块所有权边界见[根 Design](../DESIGN.md)和[根 Architecture](../ARCHITECTURE.md)；精确状态机、事务和投递行为只见[本级 Contract](CONTRACT.md)。

## 将机会事实与投递结果分开保存

市场派生值可重建，但“系统当时观察到机会并提交了事件”是应用事实，不能被后来的 Raw/参考修订或通知结果覆盖。为恢复和解释保留规则、前后输入及缺口，承认轮询只能发现观察之间的变化，不声称完整捕获每次穿越。这也使去重来自已提交状态，而不是通知发送是否成功。

将事件提交与状态推进作为同一原子动作，再由内部通知 adapter 消费，可以避免通知失败反向改变判断。v1 用同一 application SQLite 和一个独立进程内的两个循环满足这个真实失败模式，不引入消息队列或独立通知服务。网络送达和本地登记无法原子完成，因此保留不确定性、有限重试和稳定事件身份，不承诺端到端 exactly-once。
